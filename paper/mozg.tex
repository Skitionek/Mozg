\title[Mozg: A ``Slow by Design'' Federated Query Layer]
      {Mozg: A ``Slow by Design'' Federated Query Layer\texorpdfstring{\\}{ }
       for Heterogeneous Data Sources via GraphQL}

\author{Dominik Maszczyk}
\affiliation{%
  \institution{Independent Research}
  \city{Copenhagen}
  \country{Denmark}}
\email{skitionek@gmail.com}

\begin{abstract}
Modern data ecosystems fragment knowledge across relational databases,
graph stores, search engines, web APIs, and domain-specific
repositories.  Integrating these silos typically requires either a costly
centralised data warehouse or bespoke per-integration middleware.
This paper presents \textbf{Mozg} (Polish: \emph{brain}), an open-source
federated query layer that exposes a single GraphQL endpoint over
fourteen kinds of source, traverses user-defined and catalog-declared
relationships across them at query time, and never stores the
underlying data.  Mozg deliberately trades query latency for data
freshness, flexibility, and minimal operational
overhead---a philosophy called \emph{``slow by design''}.
The architecture, driver model, ontology-ingestion pipeline,
and browser-based query builder are described, together with a
catalog of 90 ready-to-query sources.  Forty-seven of them are public
life-science APIs described declaratively (206 entities, 663 relations,
441 of which cross from one source to another) and joined through
\emph{OBO keys}: identifier spaces named by their Bioregistry prefix,
under the rule that two fields with the same key and the same value
denote the same thing.  A Helm chart hosts copies of large databases on
any of six engines next to Mozg, scales each to zero when idle, and
wakes it on the next query.  The evaluation covers an automated suite of
745 tests, a connector evaluation against real servers that found and
fixed fifteen defects, static and live verification of the catalog,
ontology ingestion up to 256\,680 triples, and server-side overhead
below one millisecond per query.
\end{abstract}

\keywords{federated queries, GraphQL, heterogeneous data integration,
          ontology mapping, data virtualisation, cross-database joins,
          life-science identifiers, scale-to-zero}

\section{Introduction}
\label{sec:intro}
% ===============================================================

The proliferation of specialised data stores---relational databases,
property-graph engines, triple stores, document databases, search
engines, and web APIs---creates what is commonly called the
\emph{data silo} problem~\cite{halevy2006data}.  Organisations that
need to ask questions spanning multiple silos face an uncomfortable
choice: build a data warehouse that periodically copies and integrates
data, or write custom integration code for each pair of sources.
Both options introduce significant cost: warehouses require ETL
pipelines, transformation logic, and storage duplication; bespoke code
is hard to maintain and becomes stale the moment source schemas evolve.

\textbf{Mozg} takes a third approach.  Instead of centralising data, it
centralises the \emph{ability to query} data.  Users describe the
connections between entities in different systems---a
\texttt{hasMany}/\texttt{hasOne}/\texttt{belongsTo} relationship lattice
that mirrors familiar ORM conventions---and Mozg resolves these
relationships at query time, returning a joined result without ever
persisting a copy of the underlying records.  The single entry-point
is a GraphQL endpoint; users supply their own database credentials
or API keys as part of each query, keeping the server stateless with
respect to authorisation.

This non-aggregating design has two important practical consequences
that are absent from most existing solutions.  First, it substantially
lowers the barrier to collaborative development: multiple teams can
share a single Mozg endpoint configuration that spans \emph{their own,
separately-held} databases without granting one another direct access
to any underlying store.  Second, and critically for scientific and
open-data ecosystems, it respects the \emph{read-only access policies}
of many public databases.  Copying and redistributing data from sources
licensed for read-only or non-commercial access---as a conventional
data warehouse would---may violate those terms; Mozg avoids this
entirely because data never leaves its origin server.

The life sciences are the setting where this matters most, and the
current version of Mozg is built around them.  Public biological
databases are numerous, independently operated, and joined in practice
by shared identifiers: a UniProt accession, an Ensembl gene, a ChEBI
compound.  Mozg ships executable descriptions of 47 such services and a
single rule for joining them, described in Section~\ref{sec:catalog}.

The name alludes to the system's role as a \emph{cognitive layer}: like
a brain, Mozg does not store memories---it connects them.  The
``slow by design'' label is not an apology but a deliberate design
decision: latency is accepted as the price of freshness and schema
flexibility.  This trade-off is appropriate for interactive exploration,
scientific data synthesis, and ad-hoc cross-domain analytics where
staleness is unacceptable.

\section{Background and Related Work}
\label{sec:background}
% ===============================================================

\subsection{Federated Query Systems}

Federated databases were formalised by Sheth and Larson~\cite{sheth1990federated},
who classified multi-database systems along axes of autonomy and
heterogeneity.  Classical systems such as IBM's Garlic~\cite{haas1997optimizing}
and TSIMMIS~\cite{hammer1995tsimmis} translate a unified query language
into source-specific sub-queries.  More recent systems include Presto
(now Trino)~\cite{sethi2019presto}, which federates analytical SQL over
HDFS, Hive, and relational stores, and Apache Drill~\cite{hausenblas2013apache},
which enables schema-free SQL across Hadoop and NoSQL backends.

\subsection{GraphQL as a Query Interface}

GraphQL~\cite{graphql2015} was introduced by Facebook in 2015 as a
typed query language for APIs.  Its hierarchical, declarative nature
maps well to the entity--relationship model.  GraphQL Federation
(Apollo Federation)~\cite{apollofederation} distributes a single
GraphQL schema across multiple microservices and sub-graphs.  Unlike
Apollo Federation, which federates GraphQL \emph{services},
Mozg federates \emph{raw data sources} that are not themselves GraphQL
services.

GraphQL Mesh~\cite{graphqlmesh} provides source handlers that translate
a unified GraphQL schema into REST, gRPC, SOAP, OpenAPI and database
calls.  Mozg uses GraphQL Mesh handlers for six backends (MySQL, Neo4j,
OpenAPI, SOAP, OData, Thrift), queries PostgreSQL and SQLite through
Knex~\cite{knex}, keeps its own drivers for the remaining sources, and
provides its own relation-traversal layer on top of all of them.

Hasura~\cite{hasura} generates a GraphQL API automatically from
PostgreSQL, MySQL, and a growing set of other relational sources and
federates them via \emph{Remote Schemas}.  Prisma~\cite{prisma} is an
ORM and data-access layer that offers GraphQL-compatible typed queries
over SQL and MongoDB backends.  PostGraphile~\cite{postgraphile} generates
a full GraphQL schema by introspecting a single PostgreSQL database.
Dgraph~\cite{dgraph} is a natively graph-oriented database that exposes
a GraphQL interface.

A crucial distinction separates all of these systems from Mozg:
\textbf{each of them targets a single database (or a homogeneous cluster
of the same database technology) as its primary backend}.  They are
GraphQL \emph{wrappers} around one data store, not abstraction layers
over many independently-operated, heterogeneous sources.  Hasura's
Remote Schemas feature and Prisma's multi-provider support edge towards
federation, but both still require the operator to own and configure
every connected backend.  Mozg, by contrast, queries sources that the
server operator does not own or control---public web APIs, third-party
relational databases, domain-specific repositories---using credentials
supplied at query time by the client.  This architecture is
fundamentally different: \textbf{Mozg never aggregates data into a
central store}.  As a result, it enables collaborative
cross-organisation queries without requiring any party to share
database access credentials, replicate data, or risk violating the
read-only or non-commercial redistribution terms attached to many
public scientific databases.

\subsection{Data Virtualisation}

Data virtualisation~\cite{datavirt} provides a logical, unified view of
distributed data without physical integration.  Commercial products such
as Denodo, TIBCO Data Virtualization, and IBM Federation Server occupy
this space.  Mozg is a lightweight, open-source alternative positioned
for exploratory use: it does not implement cost-based query
optimisation, cross-source pushdown strategies, or persistent schema
registries.

\subsection{Semantic Web and Ontology Mapping}

OWL (Web Ontology Language)~\cite{owl2} and RDFS define vocabularies and
axioms for machine-readable knowledge.  Systems such as
Ontop~\cite{ontop} and D2RQ~\cite{d2rq} map OWL/SPARQL queries onto
relational databases (SPARQL-to-SQL rewriting).  Mozg's ontology
pipeline moves in the opposite direction: given an OWL TBox, it
generates GraphQL type definitions and entity maps that can then be
used to drive its federated query layer.

\subsection{Identifiers in the Life Sciences}

Biological databases refer to one another through identifiers rather
than through shared schemas.  The OBO Foundry~\cite{obofoundry}
coordinates biomedical ontologies whose terms are written as compact
URIs (CURIEs) such as \texttt{GO:0006915}, and the
Bioregistry~\cite{bioregistry} records, for over a thousand identifier
spaces, a canonical prefix, the preferred way to write it, and a
pattern its local identifiers must match.  Mozg uses these prefixes as
join keys (Section~\ref{sec:obo}): rather than mapping every pair of
sources, it records which identifier space each field and parameter
holds.

Figure~\ref{fig:arch} shows the layers of Mozg.

\paragraph{HTTP Server (\textup{\texttt{src/index.js}}).}
A Node.js server built on \emph{graphql-yoga}~\cite{graphqlyoga}
listens on a configurable port (default 4000).  It exposes
\texttt{/graphql} for the GraphQL endpoint and GraphiQL IDE,
\texttt{/stream} for progressive results (Section~\ref{sec:stream}),
\texttt{/demand/<source>} for the autoscaler of self-hosted databases
(Section~\ref{sec:selfhost}), \texttt{/healthz} for liveness probes,
and the browser query builder at \texttt{/}.  A lightweight
static-file handler serves the \texttt{public/} directory; it decodes
each request path and checks that the resolved file lies inside the
document root.

\paragraph{GraphQL Schema (\textup{\texttt{src/schema.js}}).}
A hand-written SDL schema defines the full type system.  Its root
query fields are:
\begin{itemize}
  \item \texttt{query(input: QueryInput!)} --- executes a federated
        multi-source query with optional relation traversal;
  \item \texttt{introspect(connection, source)} --- returns the schema
        of a remote database or catalog source (tables, columns, types,
        nullability, primary-key flags);
  \item \texttt{catalog(name, category, driver)} --- returns catalog
        entries, with each entity's parameters, fields, relations and
        implicit links;
  \item \texttt{oboKeys} --- lists the identifier spaces Mozg knows
        (Section~\ref{sec:obo});
  \item \texttt{generateSchema(input)} --- maps an OWL ontology to
        GraphQL SDL without side effects.
\end{itemize}
The mutation \texttt{ingestOntology(input)} parses an OWL ontology,
caches the result, and can validate it against a live database.  A
custom \texttt{JSON} scalar accepts arbitrary structured values so that
heterogeneous query results can be returned without a fixed schema.

\paragraph{Query Connector (\textup{\texttt{src/database/connector.js}}).}
A routing layer that turns a catalog \texttt{source} into a connection,
resolves the \texttt{driver} of the connection through the driver
registry, delegates execution, and follows relations that leave the
source.  Queries to self-hosted databases are wrapped in
\texttt{withWake} (Section~\ref{sec:selfhost}).

\paragraph{Driver Registry (\textup{\texttt{src/database/registry.js}}).}
The single source of truth for driver bindings.  It maps the fourteen
driver names (\texttt{postgres}, \texttt{mysql}, \texttt{sqlite3},
\texttt{neo4j}, \texttt{arango}, \texttt{elasticsearch},
\texttt{biocyc}, \texttt{api}, \texttt{rest}, \texttt{kegg},
\texttt{openapi}, \texttt{soap}, \texttt{odata}, \texttt{thrift}) to
their implementing modules.

\paragraph{Driver Implementations (\textup{\texttt{src/database/drivers/}}).}
Each driver exposes a uniform interface: \texttt{executeQuery(input)}
and, optionally, \texttt{introspect(connection)}.
Section~\ref{sec:drivers} describes them.

\paragraph{Shared HTTP Client (\textup{\texttt{src/database/http.js}}).}
Every driver that reaches a source over HTTP goes through one client.
Public life-science APIs are shared infrastructure run on research
budgets, and a query that fans out across relations can issue hundreds
of requests, so the client is deliberately polite and patient:
\begin{itemize}
  \item every request has a timeout (30\,s by default), so one hung
        upstream cannot hang a query;
  \item transient failures (408, 429, 502--504, timeouts, resets) are
        retried with exponential backoff, honouring
        \texttt{Retry-After};
  \item requests to one host are throttled to that host's published
        rate limit and, by default, to four in flight at once;
  \item identical GET requests already in flight share one round-trip,
        which matters when many parent rows point at the same record;
  \item API keys are masked in every error message, and an HTTP error
        keeps its underlying network cause.
\end{itemize}
Responses are not cached by default; a short in-process cache can be
enabled when latency matters more than freshness.

\subsection{Query Execution Flow}

When a client issues a \texttt{query} request, the server:
\begin{enumerate}
  \item Parses the \texttt{QueryInput}: a catalog \texttt{source} or an
        explicit connection, the entity, columns, predicates,
        limit/offset/orderBy, explicit \texttt{relations}, and catalog
        relations to \texttt{include}.
  \item Resolves the connection (from the catalog when \texttt{source}
        is given; explicit connection fields override it) and the
        driver, and calls \texttt{executeQuery}.
  \item The driver issues the primary query against the target source.
  \item Each relation is resolved by one shared routine, so every
        driver agrees on what \texttt{hasMany}, \texttt{hasOne} and
        \texttt{belongsTo} mean.  SQL, AQL and Elasticsearch drivers
        fetch a same-source relation for all parent rows in one query;
        the REST, Mesh and \texttt{api} drivers issue one request per
        parent row, with at most four in flight (per host, for HTTP
        sources).  Relations into another source are resolved through
        that source's own driver.
  \item Results are merged and returned as a \texttt{QueryResult}
        with a \texttt{count} and a JSON \texttt{data} array.
\end{enumerate}

This is a nested-loop join executed in application code.
Semantically, relation resolution is a \emph{left outer join}:
the primary result set is always returned in full; each relation field
is populated with a (possibly empty) array of matched sub-records.
The design deliberately avoids cross-source optimisation; it is simple
to implement, easy to debug, and independent of any particular source's
query planner.  Relation definitions can be nested to arbitrary depth,
enabling multi-hop traversals across heterogeneous sources.

\subsection{Query Model Semantics}
\label{sec:semantics}

Let $Q = (\mathit{src}, F, \sigma, o, \rho, \lambda, R)$
denote a \texttt{QueryInput}, where:
$\mathit{src}$ is the entity name (table, label, index, or API path);
$F$ is the set of selected fields ($\emptyset$ means all);
$\sigma$ is a conjunction of equality predicates on $\mathit{src}$;
$o$ is an optional \textsc{orderby}/direction pair;
$\rho$ is an offset;
$\lambda$ is a non-negative integer limit ($\infty$ if absent);
$R$ is a list of \emph{relation sub-queries}.

The result of evaluating $Q$ against a source $S$ is defined as:

\begin{enumerate}
  \item The primary query, with predicates applied before ordering,
        offset, and limit:
        \[ T \leftarrow \Pi_F\bigl(\mathrm{lim}_\lambda(\mathrm{off}_\rho(\mathrm{sort}_o(\sigma(\text{scan}(S, \mathit{src})))))\bigr). \]
  \item For each $r_i \in T$ and each relation
        \[ (S', \mathit{src'}, k_\ell, k_f, k_o, \tau, \lambda', Q') \in R, \]
        where $k_\ell$, $k_f$ and $k_o$ are the local, foreign and
        owner keys, let $X' = \text{scan}(S', \mathit{src'})$.
        If $\tau \in \{\texttt{hasMany},\,\texttt{hasOne}\}$,
        \[ r_i[\text{alias}] \leftarrow \mathrm{lim}_{\lambda'}\{r' \in X' \mid r'[k_f] = r_i[k_\ell]\}, \]
        with $\lambda' = 1$ for \texttt{hasOne}.
        If $\tau = \texttt{belongsTo}$,
        \[ r_i[\text{alias}] \leftarrow \{r' \in X' \mid r'[k_o] = r_i[k_f]\}[0]. \]
        If the sub-fetch fails, $r_i[\text{alias}]$ is set to an
        \texttt{\{error\}} marker; the primary row is preserved.
  \item Step 2 recurses on $Q'$ if nested relations are present.
\end{enumerate}

When a relation is declared by an OBO key $\kappa$
(Section~\ref{sec:obo}), equality is taken between canonical forms:
$\nu_\kappa(r'[k_f]) = \nu_\kappa(r_i[k_\ell])$, where $\nu_\kappa$
writes a value of identifier space $\kappa$ in its one canonical way,
and a value from a different identifier space matches nothing.

The predicate $\sigma$ is applied only to the \emph{primary} query.
Predicates on related entities are specified in the nested
\texttt{RelationInput.where} field.  The limit $\lambda$ applies to the
primary entity; $\lambda'$ bounds the related rows \emph{per parent
row}, and is pushed into SQL with
\texttt{row\_number() over (partition by \ldots)} and into AQL with a
limited sub-query per parent.  Recursive evaluation terminates when no
further \texttt{RelationInput} nodes remain.

\subsection{Connection Model}

Mozg is deliberately \emph{stateless} with respect to credentials.
All connection parameters (host, port, database name, username,
password, authentication scheme, HTTP headers) and optional API keys
are supplied by the client on every request.  The server maintains
in-memory connection caches whose keys include every connection
parameter, password included, so a request with a wrong password can
never reuse a connection authenticated by another caller.  Credentials
are not persisted to disk or a secrets store.  This design
simplifies the threat model: the server is not a credential vault and
does not require secret-management infrastructure.

The one exception is a database hosted alongside Mozg
(Section~\ref{sec:selfhost}): its catalog entry takes its connection
from the server's environment, which the deployment fills from a
Kubernetes Secret.  Such a \emph{server-held} connection is never
returned to callers, and a query cannot override its fields.
\textbf{Deployments must enforce HTTPS} to prevent credential
interception in transit; running Mozg over plain HTTP should be
restricted to loopback or private-network contexts only.

\section{Driver Model}
\label{sec:drivers}
% ===============================================================

\subsection{Declarative API Driver}

Public life-science APIs share almost nothing beyond HTTP.  Identifiers
go in the path for one (\texttt{/uniprotkb/P04637}) and in the query
string for the next; records arrive bare, under \texttt{results}, or
keyed by the identifier requested; pagination is \texttt{size},
\texttt{limit}, \texttt{rows}, \texttt{pageSize}, or absent.  A generic
REST driver that guesses at these conventions gets most of them wrong,
so the \texttt{api} driver guesses nothing.  Each catalog entry
describes its entities, and the driver executes that description:
\begin{itemize}
  \item the request: a path with \texttt{\{placeholders\}}, the method,
        query-string parameters, a JSON body, or a GraphQL query with
        variables;
  \item the response: its format (JSON, TSV, text, or XML), where the
        records are, and which fields to keep under which names, written
        in a small path language (nested properties \texttt{a.b},
        indices \texttt{a[0].b}, mapping over arrays \texttt{a[].b},
        and alternatives \texttt{a|b});
  \item paging, the statuses that mean ``no records'', and, for
        lookups that need several requests, a resolver function;
  \item an example, which the verification tooling runs
        (Section~\ref{sec:verification}).
\end{itemize}
\texttt{where} keys are the entity's declared parameters; an unknown key
is an error, never a silently ignored filter.  This is what lets the
generic relation resolver join across sources: a relation sets the
target entity's parameter from a field of the parent row, and the
target's description decides whether that becomes a path segment, a
query parameter, or a GraphQL variable.

\subsection{Knex Drivers: PostgreSQL and SQLite3}

PostgreSQL and SQLite3 are queried through \emph{Knex}~\cite{knex}.
User-supplied identifiers (table and column names) are passed as Knex
identifiers, and every predicate value is bound as a query parameter.
Same-source relations are fetched for all parent rows in one query,
with per-parent limits applied in SQL.  PostgreSQL introspection reads
\texttt{pg\_catalog}.

\subsection{GraphQL Mesh Adapter}

The \texttt{mesh-adapter.js} driver provides a unified implementation
for the six source types handled by GraphQL Mesh handlers:
\texttt{mysql}, \texttt{neo4j} (\texttt{@neo4j/graphql}~7),
\texttt{openapi}, \texttt{soap}, \texttt{odata}, and \texttt{thrift}.
Each handler generates its own schema from the remote source's metadata
(the MySQL information schema, an OpenAPI document, a WSDL); the
adapter builds an operation over that schema and presents the uniform
\texttt{executeQuery}/\texttt{introspect} interface.  Every
filter value travels as a GraphQL variable coerced to the type the
handler's schema declares, and field names are checked against that
schema first.  OData requests push paging, ordering, and equality
filters to the server.  Handler instances are cached per connection,
password included.

\subsection{ArangoDB and Elasticsearch Drivers}

The ArangoDB driver uses the official \emph{arangojs}~\cite{arangojs}
client and translates \texttt{QueryInput} into AQL
\texttt{FOR}/\texttt{FILTER}/\texttt{SORT}/\texttt{LIMIT} clauses.
Collection names and attribute names travel as bind parameters
(\texttt{@@coll}, \texttt{doc[@attr]}), like every value.  The
Elasticsearch driver searches an index: \texttt{where} becomes
exact-match filters on keyword forms, paging and ordering become
\texttt{size}, \texttt{from} and \texttt{sort}, relations are one
batched query each, and introspection reads the index mappings.

\subsection{REST Driver}

The plain REST driver maps \texttt{QueryInput} fields to HTTP GET
requests against a base URL.  \texttt{belongsTo} fetches the record a
foreign key names (an id or a URL); \texttt{hasMany} passes the parent's
local key as a query parameter named after the foreign key, or follows a
list of ids or URLs held by the parent, and URLs found in data are followed only on the
connection's own origin.  A catalog entry can name an API's paging
parameters (a name set to null means that step is done client-side),
envelope keys, default headers, and a rate limit; a foreign key can be a
path into the parent (\texttt{types[].type.url}).

\subsection{BioCyc Driver}

The BioCyc driver integrates with the BioCyc~\cite{biocyc} collection
of metabolic pathway databases through the documented
\texttt{apixml} web service (function
\texttt{get-class-all-instances}).  Related frames
are resolved from one listing of their class rather than one request
per identifier.  Anonymous access is rationed by the provider, so real
use needs a BioCyc account.

\subsection{KEGG Driver}

KEGG~\cite{kegg} (Kyoto Encyclopedia of Genes and Genomes) exposes its
REST API (\texttt{rest.kegg.jp}) as \texttt{text/plain} responses rather
than JSON.  The dedicated \texttt{kegg} driver transparently converts
these responses before they reach the query layer:

\begin{itemize}
  \item \textbf{Tab-delimited format} (used by \texttt{/list},
        \texttt{/find}, and \texttt{/link}) is parsed into row objects
        with fields \texttt{entry\_id}/\texttt{name} or
        \texttt{source\_id}/\texttt{target\_id} depending on the
        endpoint family.
  \item \textbf{KEGG flat-file format} (used by \texttt{/get}) is parsed
        into a single record object whose keys correspond to KEGG
        field names (e.g.\ \texttt{entry}, \texttt{formula},
        \texttt{pathway}) with repeated fields accumulated into arrays.
\end{itemize}

Because KEGG encodes query terms as URL \emph{path} segments rather
than query-string parameters (e.g.\ \texttt{/find/compound/glucose}),
the driver introduces a special \texttt{where.\_pathSuffix} convention:
any value supplied under that key is appended to the entity path
before the HTTP request is issued.

\section{Source Catalog and OBO Keys}
\label{sec:catalog}
% ===============================================================

\subsection{Catalog Contents}

Mozg ships a catalog of 90 sources, each described in one file under
\texttt{src/catalog/}.  Forty-seven are public life-science APIs served
by the \texttt{api} driver, in nine categories:

\begin{itemize}
  \item \textbf{Genes \& genomes}: Ensembl, NCBI Gene, HGNC, MyGene.info,
        the Alliance of Genome Resources, FlyBase, GenBank, NCBI
        E-utilities, ENA;
  \item \textbf{Proteins \& structures}: UniProt, PDB, PDBe, AlphaFold
        DB, InterPro, RNAcentral;
  \item \textbf{Interactions \& pathways}: STRING, IntAct, Reactome,
        Rhea, RegulonDB (and KEGG, through its own driver);
  \item \textbf{Function \& ontologies}: QuickGO, the Gene
        Ontology~\cite{go} API, OLS, HPO, MeSH;
  \item \textbf{Chemistry \& drugs}: ChEMBL, PubChem, ChEBI, LIPID MAPS,
        RxNorm, openFDA, DGIdb;
  \item \textbf{Disease \& variants}: Open Targets, Monarch, the GWAS
        Catalog, ClinVar, MyVariant.info, gnomAD, CIViC;
  \item \textbf{Clinical}: ClinicalTrials.gov;
  \item \textbf{Literature}: PubMed, Europe PMC;
  \item \textbf{Expression \& samples}: GTEx, the Human Protein Atlas,
        GEO, BioSamples, PRIDE.
\end{itemize}

Together these describe 206 entities and 663 relations; 441 relations
lead from one source into another, and 529 are declared by OBO key
rather than by field names.  The remaining 43 entries are 20 public
REST demonstration APIs (PokéAPI, JSONPlaceholder, Open-Meteo, SWAPI,
MusicBrainz, and others), KEGG, 18 BioCyc pathway/genome databases,
two SQLite samples, the Rfam public MySQL server, and the Neo4j Movies
demonstration graph.  Catalog files are loaded lazily on first access.

A catalog source is queried by name; it supplies the connection, and
four \texttt{QueryInput} fields build on it:
\begin{itemize}
  \item \texttt{source} names the catalog entry;
  \item \texttt{include} follows catalog relations by alias; dots go
        deeper (\texttt{"mechanisms.target"}), across sources where
        needed;
  \item \texttt{apiKeys} passes optional keys per source, applied to the
        queried source and every related one, which raise a provider's
        rate limit and never appear in error messages;
  \item \texttt{raw} returns records exactly as the source sent them,
        for fields the catalog does not map.
\end{itemize}

\begin{lstlisting}[language=GraphQL,caption={One protein, its structures, predicted model, pathways and drug-target record: five databases, one query.},label={lst:uniprot}]
{ query(input: {
  source: "uniprot"  from: "protein"
  where: { uniprotAccession: "P04637" }
  select: ["uniprotAccession", "symbol",
           "name", "ensemblGeneId"]
  include: ["structures", "alphafold",
            "pathways", "target"]
}) { count data } }
\end{lstlisting}

\subsection{OBO Keys}
\label{sec:obo}

An \emph{OBO key} is the Bioregistry~\cite{bioregistry} prefix of an
identifier space---\texttt{uniprot}, \texttt{ensembl},
\texttt{ncbigene}, \texttt{chebi}, \texttt{mondo}---as OBO
files~\cite{obofoundry} use it in their cross-references.  Mozg defines
56 keys, each with its preferred prefix, a pattern for its local
identifiers, and, where they exist, synonyms seen in the wild.
Annotating fields and parameters with these keys gives Mozg one rule
that replaces most hand-written joins:
\begin{quote}
  \emph{Two fields with the same OBO key and the same value name the
  same thing.}
\end{quote}

\paragraph{Canonical forms.}
For the rule to hold, every keyed value must be written one way,
whatever source it came from.  Each key therefore has a canonical form,
to which the \texttt{api} driver normalises keyed fields:
\texttt{curie} keys are written as OBO-style CURIEs with the registry's
preferred prefix (\texttt{CHEBI:15365}, \texttt{GO:0006915},
\texttt{HGNC:11998}), because that is how their own authorities write
them; \texttt{local} keys are written as the bare local identifier
(\texttt{P04637}, an unversioned \texttt{ENSG00000141510},
\texttt{7157}).  A field that holds CURIEs from several identifier
spaces (a disease identifier may be MONDO, EFO, Orphanet, or OMIM) has
the key \texttt{*}: each value carries its own prefix, which names its
key.  Rows from SQL tables and graph labels are normalised the same
way, through the keys annotated on their columns.

\paragraph{Relations by key.}
A relation from UniProt to PDBe's \texttt{bestStructures} entity is
declared only as \texttt{obo:~"uniprot"}; it names no fields.  Mozg
finds the parent's field carrying the key and the target's parameter
accepting it, and refuses to guess when either is ambiguous.  Before the join, the value
is converted to the form the target expects; a value from an identifier
space the target cannot take resolves to nothing rather than to a query
that would match something else.

\paragraph{Implicit links.}
Because the rule holds everywhere, relations need not be declared at
all.  Every entity, in any source, whose one required parameter accepts
a key that a field of the current entity carries is an \emph{implicit
link}, named \texttt{source/entity}, or \texttt{source/entity(field)}
when the value comes from a field other than the key's canonical one.
The \texttt{catalog} query lists each entity's links, and
\texttt{include} follows them like declared relations:

\begin{lstlisting}[language=GraphQL,caption={Rows of a self-hosted database joined to two public sources by OBO key, with no relation declared.},label={lst:implicit}]
{ query(input: {
  source: "my-targets"  from: "target"
  include: ["uniprot/protein(uniprot_ac)",
    "opentargets/target(ensembl_gene)"]
}) { count data } }
\end{lstlisting}

\paragraph{Stored forms.}
A self-hosted table may store a keyed column in a form other than the
canonical one; Reactome's graph, for example, keeps ChEBI identifiers
as bare numbers.  Its entity says so with
\texttt{oboForm: \{column: "local"\}}, and join values are written that
way so the lookup matches.

\subsection{Verification}
\label{sec:verification}

A catalog that describes hundreds of relations can describe many that
never resolve.  Two layers of checks guard against that.

\paragraph{Static lint.}
\texttt{src/database/catalog-lint.js} checks, with no network access,
that every entry is executable as described and that its relations can
resolve: a relation sets the target's parameter from a field of the
parent row, so the foreign key must be a parameter the target declares
and the local key a field the parent carries; OBO keys must be known,
and a relation declared by key must find exactly one field and one
parameter.  The lint runs in the unit-test suite.

\paragraph{Live verification.}
\texttt{scripts/verify-sources.js} runs each entity's declared example
through the real query path, checks that rows come back and which
declared fields were populated, then follows every relation from the
first row.  Outcomes distinguish a catalog error (\emph{empty} or
\emph{broken}) from an upstream that is having a bad day
(\emph{unavailable}: 5xx, 429, or timeout), so provider downtime never
fails the check.  Section~\ref{sec:eval-catalog} reports the result.

\section{OWL Ontology Pipeline}
\label{sec:ontology}
% ===============================================================

A key distinguishing feature of Mozg is its ability to consume
OWL ontologies and convert them into queryable GraphQL schemas.
The pipeline has three stages: \emph{parsing}, \emph{extraction},
and \emph{mapping}.

\subsection{Parsing}

Mozg supports four serialisation formats:

\begin{itemize}
  \item \textbf{Turtle} (.ttl) --- parsed using the \emph{N3.js}
        library~\cite{n3js} via a streaming quad parser;
  \item \textbf{RDF/XML} (.rdf, .owl) --- parsed using
        \emph{rdfxml-streaming-parser}~\cite{rdfxmlparser};
  \item \textbf{OWL/XML} --- parsed using \emph{fast-xml-parser}~\cite{fxp}
        with a custom OWL/XML extractor;
  \item \textbf{Manchester Syntax} (.omn) --- parsed with a hand-written
        recursive-descent parser.
\end{itemize}

Format auto-detection inspects the HTTP \texttt{Content-Type} header,
file extension, and content heuristics (BOM, XML declaration,
Turtle prefix declarations) in that order.  Parsed quads are
normalised into a common internal representation before being passed
to the extraction stage.

An ontology can be supplied as content or as a URL that the server
fetches.  URL fetches accept only \texttt{http} and \texttt{https},
refuse literal private IPv4 addresses and loopback host names, time out
after 10\,s, and stop reading at 10\,MiB.

\subsection{Extraction}

The extractor walks the quad set and collects:
\begin{itemize}
  \item \textbf{OWL Classes} --- IRI, rdfs:label, rdfs:subClassOf chains,
        and owl:deprecated flag;
  \item \textbf{Object Properties} --- IRI, label, domain, range, and
        an inferred \texttt{relationType}
        (\texttt{hasMany}/\texttt{hasOne}/\texttt{belongsTo}) based on
        cardinality restrictions;
  \item \textbf{Data Properties} --- IRI, label, domain, range (XSD type
        mapped to GraphQL scalar).
\end{itemize}

\subsection{Mapping}

The mapper converts the extracted TBox into a GraphQL SDL string and
an \emph{entity map}: a mapping from type names to metadata including
IRI, inferred table name, abstract flag, field list, and relation list.
Abstract OWL classes (those that have subclasses but no data properties
of their own) are emitted as GraphQL \texttt{interface} types;
concrete classes become \texttt{type} definitions.  XSD datatypes are
mapped to GraphQL scalars: \texttt{xsd:integer}/\texttt{xsd:int}
$\to$ \texttt{Int}; \texttt{xsd:decimal}/\texttt{xsd:double}/\texttt{xsd:float}
$\to$ \texttt{Float}; \texttt{xsd:boolean} $\to$ \texttt{Boolean};
all others $\to$ \texttt{String}.

\subsection{Caching}

To avoid re-parsing the same ontology repeatedly within a session,
the pipeline maintains an in-memory cache keyed on a SHA-256 digest
of the raw ontology content.  Cache hits return the stored result
without parsing; misses trigger a full parse/extract/map cycle.

\subsection{Validation}

When the caller supplies a database \texttt{connection} alongside the
ontology input, Mozg optionally validates the generated schema against
the live database: it checks that every mapped class resolves to an
existing table and that every data property resolves to an existing
column.  Validation errors and warnings are returned in a structured
\texttt{ValidationReport}.

\section{Query Builder and Streaming}
\label{sec:ui}
% ===============================================================

To lower the barrier to entry for non-technical users, Mozg ships a
browser-based visual query builder served at the root path
(\texttt{/}).  The interface allows users to:
\begin{enumerate}
  \item Pick a catalog source and one of its entities, or select a
        driver and fill in connection parameters via a form;
  \item Pick a table or API endpoint from an auto-populated dropdown
        (populated via the \texttt{introspect} or \texttt{catalog}
        query);
  \item Choose columns to select from a checklist;
  \item Add filter conditions (column or declared parameter, value);
  \item Choose catalog relations to include, or add explicit relation
        traversals (entity, foreign key, relation type);
  \item Set pagination and sort parameters.
\end{enumerate}
The form state is continuously serialised to a GraphQL query string
and displayed in a read-only textarea so users can see and copy the
equivalent raw query.  Submitting the form issues the query and
renders the JSON response in a collapsible tree view.  An
\emph{examples} dropdown loads pre-built queries, making it easy to
explore public datasets without any prior configuration.

\subsection{Progressive Results}
\label{sec:stream}

Relations that fan out over many rows, and over slow public APIs, make
a complete answer slow to arrive.  \texttt{POST /stream} accepts the same
\texttt{QueryInput} as JSON and answers with newline-separated JSON
chunks, following the progressive-JSON pattern described by
Abramov~\cite{progressivejson}.  The first chunk is the envelope, whose
data is a placeholder string \texttt{"\$1"}; the main rows follow as
\texttt{\$1}, each carrying placeholders for its relations, and each
relation's rows arrive as their own chunk as soon as that round-trip
completes.  One placeholder corresponds to one data-source query, so a
client can render the primary rows while their relations are still in
flight.

\section{Self-Hosted Databases That Scale to Zero}
\label{sec:selfhost}
% ===============================================================

Mozg itself is stateless: the 47 life-science APIs need nothing
deployed.  A copy of a large database is worth hosting when it is
queried heavily, needs to be close, or has a full schema that an API
exposes only in part.  The Helm~\cite{helm} chart in
\texttt{deploy/helm/mozg} runs Mozg on Kubernetes and, optionally,
such databases next to it, on any of the six engines Mozg can query:
PostgreSQL~18, MariaDB~12.3 (for the \texttt{mysql} driver),
Neo4j~5.26, ArangoDB~3.12, Elasticsearch~9.5, and SQLite.  Presets
restore ChEMBL from its PostgreSQL dump and Reactome from its Neo4j
graph dump.

\paragraph{First start.}
Each server engine runs as a StatefulSet with a persistent volume.  On
its first start an init container downloads the dump (resuming after
interruptions and verifying a checksum when one is configured), the
engine loads it and any inline data, and only then is a ready marker
written and the database reported ready.  A first start that dies
part-way is detected, cleared, and retried from the dump; later starts
skip all of it.  A generated password is kept in a Secret that
survives upgrades.  A SQLite file is instead fetched by init containers
of each Mozg pod.

\paragraph{Registration and isolation.}
Each hosted database is registered with Mozg as a catalog entry whose
connection comes from the server's environment, so
\texttt{source: "chembl-postgres"} works in any query while the
connection itself stays hidden (Section~\ref{sec:architecture}).  Its
columns are annotated with OBO keys, which joins it, in both
directions, to every public source that uses those keys
(Listing~\ref{lst:implicit}).  A NetworkPolicy admits only Mozg to the
database.

\paragraph{Scale to zero.}
With KEDA~\cite{keda} installed, each database scales between zero and
one replica.  Mozg counts every query against a hosted source as
\emph{demand} while it runs and for a window afterwards (60\,s by
default), and reports it at \texttt{GET /demand/<source>}, which KEDA's
\texttt{metrics-api} trigger polls.  Each Mozg pod also asks its peers,
so scaling Mozg out does not hide demand.  After a cooldown with no
demand (15 minutes by default) the database is scaled back to zero.
Without KEDA the chart runs one replica permanently.

\paragraph{Wake on query.}
A query to a database at zero replicas finds nothing listening.
Instead of failing, \texttt{withWake} keeps retrying, backing off to
5\,s, for up to three minutes by default, while the query's own
in-flight count is what makes KEDA bring the database back.  Only
errors recognised as ``not up yet'' are retried: refused connections,
DNS failures and timeouts (\texttt{ECONNREFUSED} and related codes);
pooled connections the database closed when it scaled down (undici's
\texttt{UND\_ERR\_SOCKET}, MySQL's \texttt{PROTOCOL\_CONNECTION\_LOST});
a MySQL server that has accepted a connection but not yet greeted;
PostgreSQL's ``shutting down'' and ``starting up'' states
(\texttt{57P01}--\texttt{57P03}); and Neo4j's
\texttt{ServiceUnavailable}.  Errors that mean the query is wrong, such
as bad credentials or an unknown table, fail at once.  Introspection
waits in the same way.  ``Slow by design'' includes a cold start.

\paragraph{End-to-end tests.}
CI deploys the chart on a kind~\cite{kind} cluster with KEDA and a
small database of every engine, each holding two UniProt accessions,
and asserts, for each engine in parallel, that its database
(1)~scales to zero when idle, (2)~is woken by
a query that is then answered, (3)~joins to the public UniProt API by
OBO key, (4)~keeps its connection hidden from callers, (5)~scales back
to zero once the demand window and cooldown have passed, and (6)~is
woken again, when the query after a second cold start finds the pooled
connections of the first one dead and must still be answered.  Steps
1, 5, and 6 do not apply to SQLite, which has no server.  The test
runs once per version preset (Section~\ref{sec:eval-versions}), with
Kubernetes, kind, Helm, KEDA, Node.js and every database image taken
from the preset.

\paragraph{An upstream entrypoint defect.}
The ArangoDB image's entrypoint, from version 3.12.5 on, starts its
first-start server with the command word as a positional argument,
which \texttt{arangod} takes as its database directory:
\texttt{./arangod}, relative to \texttt{/}.  That server then created
the database and restored the dump into a directory the real server
never reads.  The chart mounts the data volume at \texttt{/arangod} as
well, so the first-start server works on the real data; on an image
with a fixed entrypoint the extra mount is simply unused.

\section{Evaluation}
\label{sec:evaluation}
% ===============================================================

Unless stated otherwise, measurements were taken on a virtual machine
with four vCPUs (Intel Xeon, 2.1\,GHz) and 15\,GB of RAM, running
Node.js 22.23.4.  The production image runs Node.js~26, the active LTS
line; CI tests three version presets (Section~\ref{sec:eval-versions}).

\subsection{Automated Tests}

The unit-test suite (\texttt{node --test tests/*.test.js}) has 745 tests
in 120 suites, all of which pass.  It covers every driver against
in-memory stand-ins or recorded response shapes, the HTTP client, OBO
key normalisation, the catalog lint, the schema, the streaming endpoint,
and the ontology pipeline.  With the coverage settings CI enforces
(\texttt{src/catalog} excluded, because its field-mapping functions run
only against real responses), line coverage is 97.57\%, branch coverage
91.21\%, and function coverage 96.22\%, against thresholds of 80\%,
90\%, and 70\%.

\subsection{Catalog Verification}
\label{sec:eval-catalog}

All 47 \texttt{api} entries pass the static lint.  A full live
verification run made 868 checks that succeeded---entity examples, and
relations followed from their first row---and one that failed, in an
identifier involving Xenbase; the catalog has since been corrected.
The run is a snapshot: public services change, and the check is
designed to be repeated.

The evaluation found sixteen defects, all fixed:
\begin{enumerate}
  \item \textbf{Every Mesh connector was broken.}  A global npm override
        of \texttt{@graphql-tools/utils}, added for a security advisory
        that affects only older versions, removed a function the Mesh
        utilities call, so every Mesh query failed.  Dropping the
        override lets npm resolve a patched version for the Mesh tree.
  \item \textbf{MySQL authentication.}  The Mesh MySQL handler's client
        speaks only \texttt{mysql\_native\_password}.  MariaDB uses it by
        default; MySQL~8.4 ships it switched off and needs server flags
        to enable it; MySQL~9 has removed it, so the connector cannot
        reach MySQL~9 at all.
  \item \textbf{MySQL paging was swapped}: the handler rendered
        \texttt{LIMIT limit,offset}, which MySQL reads as offset first.
        The adapter now asks only for a row count and skips the offset
        itself.
  \item \textbf{Mesh filters fitted one handler only.}  Raw literals
        were spliced into query text; values are now typed variables,
        and OData pushes paging, ordering and filters to the server.
  \item \textbf{Credential-blind caches.}  The Mesh and ArangoDB caches
        were keyed without the password, so a request with a wrong
        password reused a source another caller had authenticated;
        against MySQL it returned rows.
  \item \textbf{AQL injection.}  Collection names, \texttt{where} keys,
        \texttt{orderBy}, and \texttt{select} were spliced into AQL;
        they are now bind parameters.
  \item \textbf{BioCyc} called an endpoint that no longer exists.
  \item \textbf{Elasticsearch} read index metadata instead of searching,
        and dropped relations and ordering.
  \item \textbf{REST \texttt{hasMany}} fetched
        \texttt{/\{entity\}/\{parent.id\}} and so returned the wrong
        records.
  \item \textbf{Per-parent relation limits} were not honoured; they now
        are, by every connector.
  \item \textbf{Introspection} did not wait for a self-hosted database
        to wake.
  \item \textbf{The REST demo sources' relations}, followed live, mostly
        returned the wrong records, an error, or nothing; each was fixed
        and checked live, or removed where the API cannot serve the join.
  \item \textbf{Neo4j integers.}  The Mesh Neo4j transport reads
        integers as native BigInts, which the \texttt{@neo4j/graphql}~7
        BigInt scalar rejects, so any node with an integer property
        could not be read.  The integration fixture, seeded from
        JavaScript numbers that Neo4j stores as floats, missed it; the
        Helm end-to-end test, which creates its nodes in Cypher, found
        it.  BigInts are now serialised as numbers while they are safe
        integers, else as strings.
  \item \textbf{Wake errors.}  The HTTP client dropped the network cause
        of an error, and pooled connections closed by a database
        scaling down were not recognised as a cold start.
  \item \textbf{The Docker image could not load SQLite}: the prebuilt
        binding needs glibc 2.38, and the image was based on Debian~12
        (glibc 2.36).  It is now based on Debian~13, and CI opens a
        SQLite database inside the image.
  \item \textbf{Neo4j 2025 and later lost numeric filters.}  Neo4j's
        calendar releases name property types in Cypher's terms
        (\texttt{INTEGER NOT NULL}) rather than the driver's
        (\texttt{Long}); the Mesh handler's schema introspector typed
        every name it did not know as a string, so filtering on a number
        failed against Neo4j~2026.10.  The adapter now translates the
        new names back first.  The \texttt{newest} version preset
        (Section~\ref{sec:eval-versions}) found it.
\end{enumerate}
Two further cold-start defects surfaced in the Helm end-to-end tests
and were fixed: a PostgreSQL connection terminated by the server's
shutdown (\texttt{57P01}) was not treated as a cold start, and the
ArangoDB entrypoint defect described in Section~\ref{sec:selfhost}.

\subsection{Concurrency Characteristics}

Mozg is a \textbf{single-process Node.js application}, intended to be
run per user, per team, or as a small replicated deployment behind the
Helm chart.  To document the observed concurrency behaviour, 10
simultaneous requests were issued against the local SQLite source over
20 rounds.  The median wall-clock time for completing all 10 concurrent
queries was 3.05\,ms; p99 was 5.87\,ms.  Because the Node.js event loop
serialises CPU work, concurrent queries interleave around their I/O.
For CPU-bound workloads such as large ontology parsing, the event loop
would become a bottleneck; running several replicas is the recommended
mitigation.  Results are reproducible via \texttt{tests/bench.test.js}.

\subsection{Self-Hosting End to End}

The kind tests (Section~\ref{sec:selfhost}), run per engine with the
\texttt{lts} images, passed for all six engines: each database scaled to zero, was woken by a query,
answered it, joined to UniProt by OBO key, kept its connection hidden,
returned to zero, and was woken a second time.  One wake of the MariaDB
database was observed to take 18\,s from query to answer, of which up to
15\,s can be KEDA's default polling interval.  Cold starts of the other
engines were not timed; they are expected to be longer for engines that
start a JVM or replay a large store, and each is bounded by the
three-minute wake timeout.  The chart was additionally rendered and
validated with Helm~4.3.1 and kubeconform~0.8.0 against the Kubernetes
1.35 and 1.37 schemas, and a static scan with checkov reported 593
passed and no failed checks.

\section{Discussion}
\label{sec:discussion}
% ===============================================================

\subsection{Design Trade-offs}

The ``slow by design'' philosophy accepts higher latency in exchange
for:
\begin{itemize}
  \item \textbf{Freshness}: every query reads live data with no
        staleness window;
  \item \textbf{Flexibility}: any change to source schemas is
        immediately reflected without pipeline rebuilds;
  \item \textbf{Simplicity}: no ETL pipelines, no data warehouse,
        no schema registry;
  \item \textbf{Minimal server state}: the server holds no persistent
        data beyond in-memory connection and ontology caches,
        simplifying deployment;
  \item \textbf{License compliance}: because data never leaves its
        origin server, queries against databases governed by read-only
        or non-commercial redistribution terms are handled without
        violating those terms---a property that centralised
        data-warehouse approaches cannot offer;
  \item \textbf{Collaborative access without data sharing}: multiple
        organisations or research groups can expose their own databases
        through a shared Mozg configuration.  Cross-institutional
        queries become possible without any party surrendering direct
        database credentials or agreeing to data-transfer agreements,
        because each source answers only queries presented with the
        credentials its owner chooses to share;
  \item \textbf{Politeness}: throttling to each provider's published
        limit, retrying only what is transient, and caching nothing by
        default make Mozg a well-behaved client of shared public
        infrastructure, at the cost of speed.
\end{itemize}
Self-hosting with scale to zero extends the same trade-off to
infrastructure: a large database costs no compute while idle, and is
paid for with a cold start on the first query (18\,s in the one wake
that was timed, Section~\ref{sec:evaluation}).

\subsection{Known Limitations}
\label{sec:limitations}

\textbf{Deployment model.}  Mozg has no authentication of its own: it
runs any query a client sends, with the credentials the client sends.
It is intended for local use, for deployment within a trusted private
network, or behind an authenticating ingress.  The Helm chart confines
hosted databases to Mozg with a NetworkPolicy, but does not
authenticate Mozg's own callers.

\paragraph{Resolved since the previous version.}
The security issues listed in the previous version of this paper have
been addressed:
\begin{description}
  \item[SSRF (mitigated)] Ontology URL fetches are restricted to HTTP(S),
    refuse literal private IPv4 and loopback addresses, and are bounded
    in time and size.  Host names are not resolved before the check, and
    redirects are followed without re-checking, so the mitigation is
    partial.
  \item[Cypher injection] Neo4j identifiers are checked against a safe
    pattern before use, and every value is a typed GraphQL variable.
  \item[Path traversal] The static-file server decodes each request path
    and checks that the resolved file lies inside the document root.
  \item[Connection-cache collision] Cache keys include every connection
    parameter, password included.
  \item[AQL injection] Found by the connector evaluation; identifiers
    now travel as bind parameters.
  \item[BioCyc re-fetch] Related frames resolve from one listing of
    their class.
\end{description}

\paragraph{Open limitations.}
\begin{itemize}
  \item \textbf{Per-row relations.}  REST, Mesh, and \texttt{api}
        relations issue one request per parent row, with at most four
        in flight:
        REST has no generic batch filter, and the Mesh handlers' filter
        types share no \texttt{in} operator.  Wide \texttt{include}s
        over many rows are slow; \texttt{limit} on the parent query is
        the remedy.
  \item \textbf{MySQL} accounts must use the authentication plugin
        \texttt{mysql\_native\_password}, and MySQL~9, which has removed
        it, cannot be reached.
        Replacing the Mesh handler with Knex and a modern client, as was
        done for PostgreSQL, would remove the limitation.
  \item \textbf{SOAP} has no read/write distinction: naming an operation
        runs it, whatever its side effects.
  \item \textbf{Thrift} is verified only up to the transport; no public
        server was available for a round trip.
  \item \textbf{APIs that page but cannot sort} (PokéAPI) are sorted
        only within the page they return.
  \item \textbf{Ontology SDL names}: the mapper can emit duplicate field
        names and names that begin with a digit, so the SDL generated
        for real-world ontologies such as FOAF and PATO is not valid
        GraphQL.
  \item \textbf{Dependencies}: \texttt{npm audit} reports four
        moderate-severity advisories, reached through
        \texttt{@graphql-mesh/openapi}.
  \item \textbf{Public upstreams} change and fail independently of Mozg;
        live verification detects broken descriptions but cannot
        prevent them.
\end{itemize}

\paragraph{Partial-failure behaviour.}
When a relation sub-query fails (e.g., because a remote source is
temporarily unavailable or returns an HTTP error), Mozg does not abort
the entire query.  Instead, the primary result set is preserved and
the failed relation field is populated with an error marker object
(\texttt{\{"error": "relation fetch failed: \ldots"\}}) that is
visible to the client.  This ensures that a transient failure in
one source does not discard data successfully retrieved from other
sources in the same query.

\subsection{Scalability}

As a single-process Node.js application, Mozg's throughput is limited
by the event loop.  CPU-intensive ontology parsing blocks the loop:
the 256\,680-triple PATO parse took 1.9\,s.  Horizontal scaling is
straightforward because the server holds only in-memory caches that
can be cold-started per instance, and queries are independently
routable; the Helm chart can run several Mozg replicas, which share
demand for self-hosted databases with each other.  The per-host limits
of the HTTP client are, however, enforced per process, so replicas
together can exceed a provider's limit.

Within a query, relations of one level run concurrently, bounded per
host by the HTTP client, and the streaming endpoint delivers each as it
completes, but there is no
planning across sources: a relation is never reordered, merged with
another, or pushed into the source it came from.

\subsection{Future Work}

\begin{itemize}
  \item \textbf{Query optimisation}: batched relation fetches for APIs
        that accept several identifiers per request, and cross-source
        planning;
  \item \textbf{Shared rate limits}: coordinating per-host limits
        across replicas;
  \item \textbf{A Knex-based MySQL driver}, removing the
        authentication limits of the Mesh handler;
  \item \textbf{Ontology naming}: GraphQL-safe, collision-free names
        derived from labels and IRIs;
  \item \textbf{Authentication middleware}: JWT or OAuth2 bearer
        token validation in front of the endpoint;
  \item \textbf{More sources and keys}: further life-science APIs and
        self-hosted presets, joined by the same OBO-key rule;
  \item \textbf{SPARQL interface}: expose a SPARQL endpoint
        translating to the driver layer for triple-store
        compatibility;
  \item \textbf{WASM drivers}: compile lightweight database clients
        to WebAssembly to enable browser-side federation.
\end{itemize}

\section{Conclusion}
\label{sec:conclusion}
% ===============================================================

This paper presented Mozg, a ``slow by design'' federated query layer that
provides a single GraphQL interface over heterogeneous data sources.
Mozg's key contributions are:
\begin{enumerate}
  \item A \emph{driver model} that abstracts fourteen source types
        behind a uniform \texttt{executeQuery}/\texttt{introspect}
        interface, including a declarative \texttt{api} driver that
        executes catalog descriptions of web APIs;
  \item A \emph{relation-traversal engine} that joins entities across
        source boundaries at query time, with one shared definition of
        each relation type;
  \item \emph{OBO keys}, which join sources by identifier space under
        the rule that the same key and value name the same thing,
        including links nobody declared;
  \item A \emph{verified catalog} of 90 sources, including 47 public
        life-science APIs with 663 relations, checked statically and
        against the live services;
  \item \emph{Self-hosted databases that scale to zero} on six engines,
        woken by the query that needs them;
  \item An \emph{OWL ontology pipeline} that converts OWL TBox
        definitions into GraphQL schemas, and a \emph{browser-based
        query builder} for non-programmers.
\end{enumerate}

Mozg is designed for scenarios where data freshness, source
heterogeneity, and operational simplicity outweigh the need for
low latency.  By embracing this trade-off explicitly,
it enables a class of data-integration use cases that are poorly
served by traditional data warehouses or per-integration middleware.
The system is open-source and available at
\url{https://github.com/Skitionek/Mozg}.
